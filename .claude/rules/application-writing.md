# 지원서·자기소개서 작성 지침 (이 포크 전용)

> 읽는 쪽: 지원서(자기소개서 문항·프로젝트 이력 칸)를 쓰는 Claude Code 메인 세션과 하위 에이전트.
> 출처: 2026-11-24 넷마블네오 지원에서 사용자가 초안 6을 직접 고친 제출본. 전후 실제 문장은 `report/지원서-형식-비교.md`(규칙 번호 D·P가 같음), 제출본 전문은 `report/넷마블네오-자소서.md` 「제출본」.
> 우선순위: 루트 `CLAUDE.md` 원칙 1(지어내지 않음) > 이 파일 > `.claude/CLAUDE.md` 글쓰기 기본 지침·`portfolio-writing.md`. 지원서 글에서는 "쉬운 말로 풀어 쓴다"보다 이 파일의 D1(표준 용어)을 따른다.

## 독자와 톤

- 독자는 인사담당자 → 시니어 개발자 순서로 읽는다. 둘 다 업계 표준 용어를 안다고 보고 쓴다.
- 말투는 합니다체, 화자는 사용자 본인(1인칭).
- 과장하지 않는다. 내가 한 일을 한 그대로 쓴다. "주도했다", "완벽히" 같은 자랑 표현, 실적 숫자 나열은 쓰지 않는다.
- 약점·한계는 숨기지 않고 구체 대상과 보완 계획으로 쓴다.

## 자소서 문항 (D)

### D1. 표준 기술 용어로 쓴다

비개발자용으로 풀어 쓰지 않는다. 풀어 쓴 말이 떠오르면 아래 표의 용어로 바꾼다.

| 풀어 쓴 말 (쓰지 않음) | 표준 용어 |
|---|---|
| 물체 (코드상의 대상) | 객체 |
| 사라진 물체를 붙잡는 오류 | 사라진 객체를 참조하는 오류 |
| 작은 조각으로 나눈다 · 조각을 쌓는다 | 독립적으로 확인할 수 있는 단위로 나눈다 |
| 누가 누구의 작업을 기다려야 하는지 | 작업 간 의존관계 |
| 무엇을 받고 무엇을 넘기는지 | 입력과 출력 |
| 방장 컴퓨터가 계산 · 누가 보내고 누가 받는지 | 데이터의 전달과 처리 주체 |
| 측정 도구로 재 보지 못했다 · 숫자로 비교 | 정량적으로 검증 · 처리 비용과 병목 측정 |
| 꺼내고 비우는 사이에 지워짐 · 한 번에 처리 | 경쟁 상태(Race Condition) · 원자적으로 처리 |
| 죽은 몬스터를 다시 쓰는 풀 | 오브젝트 풀링 |
| 표 데이터 (파일 형식을 말할 때) | TSV 기반 |
| 코딩 에이전트(Claude Code) | Claude Code |

- 게임 안의 사물(플레이어·자원·다리)을 말할 때의 "물체"는 그대로 둔다. 코드 구조를 말할 때만 "객체".
- 프로젝트 이력 칸은 P6 용어도 따른다.

### D2. 곁가지 구체 예시를 쓰지 않는다

- 한 주장에 근거 하나만 둔다. 그 근거를 받치는 2차 예시("~처럼")·괄호 부연·기간 표기는 뺀다.
- 빼는 것의 예: 따옴표 예시("물고기를 잡는다"처럼) · 게임 고유 용어(종반 위기) · 색·키 같은 조작 세부(왼손 파랑) · 주장과 무관한 버그 일화 · (1인, 7일 기획·14일 개발) 같은 괄호 정보 · 세 경우를 다 나열한 명세.
- 세부가 꼭 필요하면 한 구로 줄인다. 예: "기존 주먹 색상과 일치하는 잡기 입력 표시".
- 같은 문항 안에서 프로젝트 역할 나열(서버·기획·PM도 했다)은 주장과 무관하면 뺀다.

### D3. 에피소드는 결과 → 배움 → 지금 적용으로 끝낸다

- 상황 → 시도 → 한계 → 추가 행동 → **결과(무엇이 달라졌나)** → **배움(~이 중요함을 배웠습니다)** → **적용(다음 프로젝트부터 ~, 현재는 ~)**.
- "깨달았습니다"로 끝내지 않는다. 그 뒤 실제로 달라진 것(예: "이후 팀원들은 … 자체적으로 연동할 수 있게 됐습니다")을 쓴다. 사실 근거가 없으면 사용자에게 묻는다.
- 도구·방법 사례는 전 → 후 변화로 쓴다. 예: "머릿속으로 계산하던 확인 과정을 화면에서 직접 확인하는 방식으로 바꾸고".
- 약점 문항도 마지막 문장은 지금 하고 있는 개선이다. 예: "현재도 ~ 방식을 개선하고 있습니다."

### D4. 지원동기는 전환점 + 직무 적합 논리로 쓴다

- 관심의 시작(분석 습관) → **실제 프로젝트에서 겪은 전환점**(예: 기능은 재현했지만 재미는 재현하지 못함) → 그 뒤 달라진 관점을 보여 준 사례 → **내 개발 방향과 직무 특성이 맞닿는 지점**.
- "성장하고 싶습니다", "배우고 싶습니다"로 끝내지 않는다. "~하려면 ~이 필요하다고 생각합니다 → ~하고 싶습니다 → 이러한 방향이 [회사]의 [직무 특성]과 맞닿아 있어 지원했습니다."
- 회사·직무 특성은 공고 원문에서만 가져온다. 해 보지 않은 회사 게임은 언급하지 않는다.

### D5. 역량 문항은 프로젝트마다 목적 → 구현 → 배운 것

- 한 프로젝트 = 한 문단: "[목적]을 위해 [구현/설계]했습니다. 이를 [구현하며/해결하며] [배운 것]을 익혔습니다(배웠습니다)."
- 마무리 문단: 세 프로젝트로 경험한 범위 한 문장 → 부족한 것 → 보완 계획을 **구체 대상**까지("몬스터 수에 따른 처리 비용과 병목을 측정").

### D6. 문장은 격식 있게 압축하고, 비유를 쓰지 않는다

- 구어·비유 대신 격식 표현: 뜯어보다 → 분석하다, 조각을 쌓다 → 단계로 나눠 확인하다, 붙잡다 → 참조하다.
- 연결어: "~을 위해", "~에 따른", "~ 및 ~", "~ 간", "~하고자 합니다", "~함을 배웠습니다".
- 목적·이유를 행동보다 앞에 둔다. 예: "설계에 대한 고민이 장기화되는 것을 방지하기 위해 30분 내에 …".
- 한 문장 한 생각. 상한의 85~100%를 채우되 넘기지 않는다.

### D7. 게임 분석은 관점마다 관찰 1 + 평가 1

- 관점 소제목을 공고 순서대로 둔다(예: [작품성] [상업성] [기술성] [재미]). 공고가 나누라고 하지 않으면 사용자에게 묻는다.
- 각 관점: 관찰한 사실 한두 문장 + **그 관점에서 왜 좋은가/아쉬운가** 한 문장.
  - 상업성: 기능 → "추천과 구매로 이어지기 좋은 구조".
  - 기술성: 잘된 것 ↔ 아쉬운 것 대비 + "직접 구현해 본 경험이 있어 눈에 띄었다".
  - 재미: 가장 즐거웠던 순간 한 장면.
- 개선안: 아쉬운 점 한 줄 → **기존 요소를 활용한** 개선 → 기대 효과("초반 조작 부담을 줄일 수 있다").

## 프로젝트 이력 칸 (P)

### P1. 첫 문단

- "[핵심 요소를 이름으로 나열]을 핵심으로 [목표]하고자 한 [장르]입니다." 또는 "[플레이 경험]하는 [장르]입니다."
- 둘째 문장은 역할과 범위: "[역할]으로서 [범위]를 담당했습니다." / "첫 Unity 개인 프로젝트로 기획부터 구현까지 전 과정을 담당했습니다."
- 시점 전환·조작 같은 세부는 쓰지 않는다.

### P2. 소제목은 프로젝트 성격별

| 성격 | 소제목 |
|---|---|
| 개인 프로젝트 | `[구현]` `[진행 방식]` `[문제 해결]` `[회고]` |
| 팀 프로젝트 | `[담당 업무]` 또는 `[주요 구현]` · `[문제 해결]`(개선 포함이면 `[문제 해결 및 개선]`) · `[결과]`(프로젝트 뒤 고친 것이 있으면 `[결과 및 후속 개선]`) |

- 굵게(`**`)는 쓰지 않는다. 지원서 칸이 마크다운을 그리는 것을 확인했을 때만 쓴다.

### P3. 구현 항목

- 개인: 명사구 시스템 이름. 동작 묘사 대신 메커니즘 이름. 예: "투사체 충돌 시점의 실드 상태를 반영하는 피해 판정 시스템".
- 팀: "~을 위해 ~을 설계/선택했습니다" 문장. 대안이 있었으면 "~하는 대신 ~ 방식을 선택했습니다"와 판단 근거(기간 등).
- 데이터 분리 항목은 효과까지: "코드 수정 없이 밸런스를 조정할 수 있도록 했습니다".

### P4. 문제 해결은 2개 안팎, 설계·동시성·과정 문제 우선

- 단순 버그(시체 낙하·중복 실행·충돌 레이어 등)는 뺀다. 설계 판단·동시성·네트워크·AI 활용 과정처럼 판단이 드러나는 문제만 둔다.
- 꼴: "[현상]하는 문제를 발견하고(가 발생했습니다), [원인 용어]를 [조치]해 해결했습니다(, ~의 중요성을 배웠습니다)."
- 판정 순서 나열(파괴 → 피해 → …) 같은 세부는 "판정 우선순위를 명확히 정의했습니다"로 줄인다.

### P5. 결과·회고

- 팀 `[결과]`: 검증 사실(최종 빌드·시연·동시 접속 인원) + 후속 개선, 또는 완성한 것 + "~의 중요성을 배웠습니다".
- 개인 `[회고]`: 완성한 것과 검증하지 못한 것 → 기술적 한계(용어로) → "~해야 한다는 설계 원칙을 얻었습니다".
- 측정하지 못한 것 같은 약점은 자소서 문항(역량 개발) 한 곳에만 쓴다. 이력 칸마다 반복하지 않는다.

### P6. 이력 칸 용어

- 방장 → 호스트, 장면 → 씬, 맡은 일 → 담당 업무, "~를 고쳤습니다" → "~를 적용해 해결했습니다".
- 자소서 문항 본문은 문맥에 따라 "방장"·"장면 전환"을 그대로 써도 된다(제출본 문항 2·4).
