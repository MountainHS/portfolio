# 이 포크만의 규칙

> 루트 `CLAUDE.md`는 `/portfolio-update`가 템플릿 원본으로 바꿉니다. 이 파일(`.claude/CLAUDE.md`)은 업데이트가 건드리지 않으므로, 이 포크에서만 쓰는 규칙은 여기에 둡니다.

## 글쓰기 기본 지침

프로젝트 문서·슬라이드·포트폴리오 페이지에 모두 적용합니다. 프로젝트 문서를 같이 쓰거나 "고쳐 줘"를 받을 때, 빌드가 장면 글을 고를 때 이 기준을 따릅니다.

- **독자는 채용 담당자·팀장입니다.** 사용자가 아닌 사람이 처음 읽어도 술술 읽혀야 합니다.
- **화자는 사용자 본인입니다.** 사용자가 채용 담당자·팀장 앞에서 자기가 만든 것을 발표하듯 설명하는 1인칭 설명문으로 씁니다("~했습니다", "다시 구현한다면 ~하겠습니다").
  - **말투는 합니다체입니다**(2026-11-20 사용자 결정). 프로젝트 문서·슬라이드·포트폴리오 페이지의 문장 끝을 "~한다/~했다" 대신 "~합니다/~했습니다"로 씁니다. 인용(`>`)한 요청 원문·코드·다이어그램 라벨·제목은 바꾸지 않습니다.
  - 글쓴이·정리자·제3자 시점 문장은 쓰지 않습니다. 예: "제작자의 회고에서는 …로 평가했다", "이 사례는 짧은 사례로 남긴다", 「보조 사례」 같은 제목, "3장의 앞 세 사례는 …이다" 같은 목차 안내.
  - 작업 보고체도 쓰지 않습니다. 퇴고하며 사용자에게 보고하던 말이 본문에 들어간 것입니다. 실제 사례(2026-11-22 Hive Purge 3장): "지금 구조가 제출본의 최종 구조입니다." · "…3.2.7절에 따로 적었습니다." · "이 표와 그림에서는 두 클래스를 '이동' 하나로 묶었습니다." 고치면: 구조 자체를 설명 · "3.1.7에서 설명합니다." · "그래서 두 클래스를 '이동' 하나로 보여 드립니다."
  - 프로젝트 문서를 쓰거나 퇴고·점검할 때 `python tools/voice-lint.py <md>`로 후보를 찾습니다. `src/<폴더>/*.md`를 Edit·Write하면 PostToolUse 훅이 넣은 글만 같은 검사로 보고, 걸리면 그 턴에 알립니다(걸린 것이 없으면 출력 없음).
  - 확인법: 사용자가 발표 자리에서 그 문장을 그대로 말해도 자연스러운지 봅니다. 정리자 메모는 `report/`에만 둡니다.
  - 개요는 게임 소개 → 핵심 경험 → 루프로 흐르고, 시스템 설명은 구조·기능 장에서 다룹니다.
- **핵심 먼저, 부가 내용은 뒤로.** 한 문단의 첫 문장이 핵심입니다. 이유·예시·조건은 그 뒤에 둡니다.
- **"A가 아니라 B"로 쓰지 않습니다.** 하려던 것(B)을 바로 씁니다. 비교 대상(A)은 꼭 필요할 때만 뒤에 짧게 둡니다.
  - 나쁜 예: "단순히 플레이어를 따라다니며 공격하는 적이 아니라, 지능적으로 포위하거나 돌진·독 장판 같은 다양한 패턴으로 공격하는 적"
  - 좋은 예: "다양한 패턴으로 공격하는 몬스터를 만들려고 했다." 다음 줄부터 `- 포위: …`, `- 돌진: …` 목록
- **목적 글의 틀:** 핵심 문장(무엇을 하려 했나) + 프로젝트 핵심 경험과 잇는 말 → 아래에 예시를 unordered list로 둡니다.
- **"왜 만들었나"(목적) 절·장면에는 플레이어 경험과 설계 의도만 씁니다.** 클래스·상태 머신·Animator 같은 구현은 구조·핵심 기능 장에서 다룹니다.
- 프로젝트 문서의 목적 절에 구현이 섞여 있으면, 빌드는 그 구현 글을 목적 장면 카드로 쓰지 않고 구조 장 앞쪽 장면으로 나눈 뒤 리포트에 알립니다.
- **개요 장은 발표처럼 흐릅니다.** 만든 게임을 "이런 경험을 의도했고 이런 루프를 가진 게임"으로 먼저 상세히 설명하고, 기술·내 담당은 뒤에서 앞 내용과 연결합니다. 기술 소개를 맨 앞에 두지 않습니다. 개요 끝에서 기술 장으로 가는 연결을 한두 문장으로 짚고, 구간별 세부는 기술 장에서 씁니다.
- **장 순서는 `개요 → 시스템 구조 → 핵심 기능 → 고민과 선택 → 결과 및 배운 점` 5장입니다.** 팀 프로젝트도 "담당 파트 개요" 장을 따로 두지 않습니다. 역할과 담당 축(루프의 어느 구간을 맡았나)은 개요 끝 "팀과 내 역할"에 두고, 담당 세부는 시스템 구조 장 도입과 핵심 기능 절 첫머리에 씁니다. 각 장 첫 문장은 앞 장의 마지막 주장을 받아 잇습니다.
- **절 이름에 따라 담는 것이 다릅니다.** "왜 만들었나"(시작 동기) 절은 시작할 때의 동기만 씁니다. "기획 의도·핵심 경험" 절은 **현재 결과**(지금 게임이 어떤 경험·루프인지)를 상세히 쓰고, 기획이 바뀐 경위(예: 생존→탐험)는 고민과 선택 절에 둡니다.
- **조작 같은 세부는 쓰지 않습니다.** "서로 붙잡아 낚시한다"처럼 의미만 쓰고, 상세는 스크린샷·그림 자리(`<!-- 촬영: … -->`)로 둡니다. 없는 이미지는 만들지 않고 촬영 목록(report)에 올립니다.
- **시각화·장면 구성 규칙**(식별자 줄바꿈·상태 머신·코드 분할·세부 수준·계층 구조·AI 활용 과정·개요 장 발표 흐름)은 `.claude/rules/portfolio-writing.md`에 있습니다. 항상 적용합니다. 파일은 `src/`·`data/`·`report/`·`format/`·포트폴리오 스킬을 읽거나 고칠 때 자동으로 실리고(그 전이면 직접 Read), `/portfolio-update` 뒤에도 남습니다. 프로젝트 문서 쓰기·점검·장면 고르기를 하위 에이전트에게 맡길 때는 브리프에 그 파일 경로와 해당 규칙 절을 붙입니다.

## report 구조

- **루트 `report.md` = 요약판.** 사용자가 오랜만에 오거나 정신없을 때 이것만 보고 다시 시작할 수 있게, 다음 네 절만 짧게 씁니다.
  1. 마지막으로 한 일 (날짜, 커밋 여부)
  2. 다시 시작할 때 할 것 (3줄 안팎, 어느 프로젝트 report의 어느 절을 보면 되는지)
  3. 리마인드 — 메모리에 "나중에 하기로 한 것"으로 남은 일(시연 영상·기간 보완·블로그 링크 등)
  4. 프로젝트별 report 표 (파일 경로 · 한 줄 상태)
- **`report/<src 폴더 이름>.md` = 프로젝트별 report.** 그 프로젝트의 할 일·"확인해 주세요"·결정 기록·질문 답변·점검 결과를 모두 여기에 둡니다. 새 내용은 맨 위 "이제 할 일"에 쓰고, 지난 것은 아래 "이전 기록"으로 내립니다.
- **질문은 한 곳에만 둡니다.** `report/` 안의 모든 파일(프로젝트별·여러 프로젝트를 묶은 계획 report 모두)에서, 사용자에게 묻는 줄은 맨 위 목록 한 곳에만 쓰고 각 질문 바로 아래에 빈 답 줄을 둡니다. 본문에 같은 질문을 다시 쓰지 않습니다. 답이 끝난 차수는 "이전 기록"으로 내립니다(2026-11-22 `피드백-반영-계획.md`에서 답 달 자리를 못 찾음).
- `report/`와 `report.md`는 둘 다 `.gitignore`에 있어 공개되지 않습니다.

## 스킬이 루트 report.md를 덮어쓸 때

`/portfolio-build`·`/portfolio-check`·`/portfolio-edit`는 루트 `report.md`에 씁니다. 스킬을 고치지 않고 다음 순서로 맞춥니다.

1. 스킬을 실행하기 **전에** 루트 `report.md`의 내용이 `report/`에 다 옮겨져 있는지 확인합니다(요약판이면 그대로 두어도 됨 — 요약판 내용은 프로젝트 report와 메모리로 다시 만들 수 있음).
2. 스킬이 끝나면 루트 `report.md`에 생긴 점검 결과를 프로젝트별로 나눠 `report/<폴더>.md` 맨 위 "이제 할 일" 아래에 옮깁니다. 이때 기존 "확인해 주세요" 줄과 사용자가 단 답(들여쓰기 줄)을 지우지 않습니다.
3. 루트 `report.md`를 위 요약판 형식으로 다시 씁니다.

- `preview.cmd`(더블클릭) 또는 `.\preview.ps1 [all|portfolio|deck|doc|report|server|stop] [프로젝트 폴더]`로 엽니다. 편집 서버(`edit-server.py`, 포트 4600)를 켜고 페이지를 브라우저로 엽니다.
- 4600 포트를 `python -m http.server`가 쓰고 있으면 편집 모드가 꺼지므로 `.\preview.ps1 stop` 뒤 다시 켭니다. 사용자에게 미리보기를 안내할 때도 이 스크립트를 먼저 알려 줍니다.
- Claude 안에서는 `/local-preview [portfolio|deck|doc|all|report|server|stop] [프로젝트 폴더]`(`.claude/skills/local-preview/`)가 같은 `preview.ps1`을 불러 엽니다. 페이지 종류를 빼면(인자 없음·폴더만) 포트폴리오 페이지만 열고, 슬라이드·상세 문서는 `deck`·`doc`·`all`을 적었을 때만 엽니다(`preview.cmd` 더블클릭·`preview.ps1` 인자 없음도 같은 기본값 `portfolio`). 이름이 `portfolio-`로 시작하지 않아 `/portfolio-update`의 교체 목록 밖입니다.

## 이 포크 전용 기능 (편집 모드·슬라이드·명령 패널)

- 자세한 규칙은 `.claude/rules/fork-features.md`에 있습니다. `assets/`·`*.html`·`data/`·`edit-server.py`·`tools/`·포트폴리오·편집 모드 스킬을 다룰 때 자동으로 실리고, 그 전에 이 기능을 고쳐야 하면 직접 Read합니다.
- **`/portfolio-build`와 `/portfolio-edit` 뒤에는 반드시** `python .claude/skills/portfolio-build/deck-edits.py apply --all` 다음에 `python .claude/skills/portfolio-build/portfolio-edits.py apply --all`을 실행합니다(편집 모드에서 고친 글을 data에 다시 덮음, 멱등).
  - 실행 전에 `git status`를 봅니다. 이번 작업 밖 프로젝트의 프로젝트 문서가 `M`이면 `--all` 대신 대상 폴더만 적용하거나 사용자에게 먼저 묻습니다(그 미커밋 수정이 data에 섞임, 2026-11-22). 커밋할 때도 세션 전부터 `M`인 파일은 `git diff`로 내 변경만인지 확인합니다.
- 슬라이드는 30~40장 권장이고, `/portfolio-build`는 장면 수를 맞추려고 장면을 빼지 않습니다. 40장을 넘을 때만 리포트에 [참고]로 알립니다.

## `/portfolio-build` 실행 방식 (토큰 절약)

- 스킬 §1의 "프로젝트마다 서브에이전트를 병렬로"는 쓰지 않습니다. 새 서브에이전트는 시작 문맥과 schema·format을 각자 다시 읽어 실행 한 번에 1~3M 토큰이 더 듭니다(2026-11-12·13 측정).
- 프로젝트 1~2개 재빌드는 메인 세션에서 차례로 합니다.
- 전체(3개 이상) 빌드는 메인에서 schema·format을 먼저 읽은 뒤, 프로젝트마다 `fork` 서브에이전트(부모 문맥을 물려받음)로 나눕니다. 효과가 없으면 메인 순차로 돌아갑니다.
- `SKILL.md`는 `/portfolio-update`가 덮어쓰므로 이 규칙은 여기에 둡니다.

## 프로젝트 문서 고민 분류 (이 포크 전용)

- 프로젝트 문서 원천 자료(회고·노트·Asana·발표·일지)에서 고민을 찾아 L1·L2·L3로 나누고, 수준별 형식 칸을 먼저 채운 초안을 `report/고민-분류/`에 쓴 뒤, 질문·답 반영·대화 세션(티키타카)으로 구체화하고 프로젝트 문서로 옮기는 절차는 `/tech-doc-issue-summary <src 폴더> [시작|답 반영|대화 Q-번호|프로젝트 문서 반영]`(`.claude/skills/tech-doc-issue-summary/`)에 있습니다. WGO 작업(2026-11-12~16)에서 쓴 방식을 옮긴 것이고, 본보기는 `report/고민-분류/WGO.md`입니다.
- `src/**`·`report/고민-분류/**`를 다룰 때만 자동으로 실립니다(`paths`). 직접 불러도 첫 인자가 `src/` 프로젝트 폴더가 아니면 실행하지 않습니다.
- 이름이 `portfolio-`로 시작하지 않아 `/portfolio-update`의 교체 목록 밖입니다.
- 고민 분류 파일(`report/고민-분류/*.md`)은 §1 상태표를 먼저 읽고, 필요한 고민은 `### <고민 ID>` 제목 줄을 Grep으로 찾아 그 절만 Read합니다. 파일 전체를 처음부터 읽지 않습니다.
