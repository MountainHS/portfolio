# 기술 문서 소스 생성 프롬프트 (프로젝트 1개 = 새 세션 1개)

사용법: 새 세션을 열고 이 파일 경로와 프로젝트 이름 하나를 준다.
예: "<이 파일 경로> 지침대로 <프로젝트> 기술 문서 소스를 만들어 줘."

# 작업 개요
작업 폴더: <작업 폴더>
한국어로 작업하고 한국어로 작성한다.
이 세션은 지정받은 프로젝트를 정확히 1개만 처리한다. 프로젝트 1개를 끝내면 다음 프로젝트로 넘어가지 말고 보고하고 끝낸다.

# 프로젝트 표
| 프로젝트 | 저장소 | 개인 정리글 | 출력 폴더 |
|---|---|---|---|
| <프로젝트> | repos/<저장소> | personal_source/<정리글 폴더> | outputv2/<프로젝트> |

저장소별 메모
- git 이력이 없는 저장소는 커밋 근거 없이 파일 근거만 쓰고, 그 사실을 "작성 메모"에 적는다.
- 클라이언트·서버처럼 저장소가 여럿이면 커밋 로그를 각각 본다. 저장소에 없는 내용을 zip 등 보조 자료로 확인했으면 그렇다고 적는다.

# 출력 규칙
- 결과 파일은 두 개다. 출력 폴더가 없으면 만든다.
  - {출력 폴더}/tech-doc-source.md: 기술 문서 소스 본문
  - {출력 폴더}/tech-doc-source-report.md: 커밋 이력 근거와 작업 기록(아래 "report 파일" 참고)
- 두 파일 중 하나라도 이미 있으면 덮어쓰지 않는다. 아무것도 쓰지 않고 "이미 있음: {경로}"라고 보고하고 끝낸다.
- 출력 폴더 안의 다른 파일(code/, _intake/, report-intake.md, 결정할것.md, 피드백 목록 등)은 고치지 않는다.

# 0단계: 읽을 자료 정하기 (역질문)
자료를 바로 다 읽지 않는다. 먼저 목록을 만들어 사용자에게 무엇을 읽을지 묻고, 답을 받은 뒤 진행한다.
1. 아래 범위의 파일 목록을 만든다. 파일 내용은 아직 열지 않는다(이름·크기·종류만 본다).
   - 이번 프로젝트의 personal_source 폴더 전체(하위 폴더 포함, zip은 `unzip -l`로 안의 파일 목록까지)
   - 이번 프로젝트의 출력 폴더(outputv2/…)에 이미 있는 파일
   - 저장소는 최상위 폴더 구조와 README 유무, git 이력 유무만
2. 같은 파일이 여러 폴더에 있으면(크기·바이트 비교) 묶어서 한 줄로 보여 준다.
3. 표로 보여 준다: 파일 경로 | 종류(md·pdf·zip·json·csv·이미지 등) | 크기 | 추천(읽음/건너뜀) | 이유 한 줄.
   - 보안 정보가 있을 수 있는 파일(키·비밀번호·ssh 등)과 팀원 개인 평가가 담긴 파일은 "건너뜀"으로 추천한다.
4. "어떤 파일을 읽을까요?"라고 묻고 턴을 끝낸다. 답을 받기 전에는 1단계 이후로 진행하지 않는다.
5. 사용자가 고른 파일만 읽는다. 읽지 않은 파일은 문서 끝 "정리글에서 쓰지 않은 내용"에 "사용자가 제외"라고 적는다.

# 기술 문서 소스 작성 (프로젝트 1개)
0단계에서 사용자 답을 받은 뒤, 아래 지침대로 {출력 폴더}/tech-doc-source.md 와 tech-doc-source-report.md 를 작성한다.

## 역할
너는 게임/소프트웨어 개발자의 포트폴리오용 기술 문서 "원천 소스"를 만드는 테크니컬 라이터다.
목표는 완성본이 아니다. 형식이 올바르고 내용이 깊은 초안 소스를 만든다. 사용자는 나중에 이 초안을 보고 피드백한다.

## 읽기 범위
- 지정한 입력 파일 밖은 읽지 않는다: <기술 문서 틀 파일(예: format/02-tech-document.md)>, 이번 프로젝트의 repos 폴더, 이번 프로젝트의 personal_source 폴더, 이번 프로젝트의 출력 폴더(outputv2/…).
- 다른 프로젝트의 repos, personal_source, 출력 폴더는 읽지 않는다.
- 예전 결과 output/ 폴더(output/0N_…/tech-doc-source.md, output/_progress.md)는 읽지 않는다. 예전 결과를 베끼지 않고 지금 근거로 새로 쓴다.

## 입력 파일과 쓰임
1. <기술 문서 틀 파일(예: format/02-tech-document.md)>: 강사가 준 기술 문서 틀이다. 문서의 형식과 판단 기준은 전부 여기를 따른다.
   - 5단 구조: 개요 → 시스템 구조 → 핵심 기능 및 사용법 → 고민과 선택(Trade-offs) → 결과 및 배운 점
   - 유형(A. 단일 기능 / B. 다기능 / C. 팀 프로젝트)은 저장소를 보고 네가 고른다. 고른 이유를 문서 맨 앞 "작성 메모"에 적고, [확인 필요] 태그를 붙인다.
   - 각 섹션의 "들어갈 내용", "👍 좋은 예", "팁"을 체크리스트로 쓴다. 예: What과 Why 분리, 측정 가능한 문제 정의, 구성요소·관계·흐름, API 먼저, 핵심 코드 50줄 이내 선별, 대안 비교와 "그냥" 금지, 데이터 기반 결과, 기술 부채와 개선 계획.
   - 크래프팅 예시는 형식 참고용이다. 내용을 가져오지 않는다.
2. repos/{저장소}: 사용자가 작업한 저장소다. 문서 내용의 1차 근거다.
   - 양이 많다. 전체를 읽지 않는다.
   - 순서: README와 폴더 구조 → 진입점과 핵심 클래스 → 커밋 로그(git 저장소면) → 필요한 파일만 깊게.
   - 3rd-party, 에셋, 자동 생성 파일(Library, Packages, .meta, 플러그인, 빌드 산출물 등)은 읽지 않는다.
3. personal_source/{정리글}: 사용자가 프로젝트 중 거칠게 적은 정리글이다.
   - 문서의 뼈대나 메인 내용으로 쓰지 않는다.
   - 문서 흐름은 기술 문서 틀과 저장소 근거로 네가 만든다.
   - 그 흐름 중 정리글과 일치하거나 보강되는 부분을 표시한다(아래 표기 규칙).
   - 고민, 느낌, 시행착오가 담긴 문장은 "고민과 선택"과 "배운 점"의 재료로 우선 활용한다.
   - md 말고 PDF·zip·json·csv도 0단계에서 사용자가 고른 것은 읽는다.
     - zip: 프로젝트 밖 임시 폴더(%TEMP% 아래 새 빈 폴더)에 풀어서 읽는다. 원본 zip과 personal_source는 건드리지 않는다. 저장소에 같은 파일이 있으면 비교해서 같은지, 어느 시점 상태인지 적는다.
     - PDF: 먼저 글자 추출을 해 본다. 한글이 빠지거나 깨지면 페이지를 그림(PNG)으로 렌더링해 읽는다. 패키지를 새로 설치하지 않고, Windows 내장 기능(Windows.Data.Pdf)을 쓰는 스크립트를 임시 폴더에 만들어 쓴다. 렌더링 결과도 임시 폴더에만 둔다. 같은 내용이 csv 등 다른 자료에 있으면 그 쪽은 그림 대신 원자료로 확인해도 된다. 어느 쪽을 어떤 방법으로 읽었는지 report에 적는다.
     - json·csv: 전체를 출력하지 않는다. 구조를 먼저 보고, 이번 문서와 관련된 행·필드만 골라 읽는다.
   - PDF·json·csv 근거 표시는 (근거: 파일명 N쪽) 또는 (근거: 파일명 "작업/항목 이름") 형식으로 한다.
4. outputv2/{출력 폴더}의 기존 파일 (있을 때만)
   - 사용자 결정 기록(_intake/결정할것.md, 피드백 목록*.md 등 사용자가 답하거나 정한 내용)은 사실로 쓴다. 이미 답한 것은 [확인 필요]로 다시 묻지 않는다. 근거 표시는 (근거: outputv2/…/파일명 항목) 형식으로 한다.
   - Claude가 만든 자료(_intake/재료집.md, _intake/촬영목록.md, report-intake.md, code/ 사본)는 단서로만 쓴다. 문서의 주장은 저장소 원본에서 다시 확인하고 저장소 경로로 근거를 단다.
   - 결정 기록과 저장소 코드가 다르면 [확인 필요]로 양쪽을 적는다.

## 작성 원칙
- 깊이 우선이다. 문장 다듬기보다 "왜 이렇게 했는가"의 근거를 코드와 구조로 보여준다.
- 지어내지 않는다. 수치(fps, 시간, 개수), 기간, 엔진 버전, 결과는 저장소나 정리글에 근거가 있을 때만 쓴다. 근거가 없으면 자리표시자를 남긴다.
- 모든 주장 옆에 근거 위치를 남긴다. 예: (근거: Assets/Scripts/<클래스>.cs:42)
- 커밋 해시와 커밋 메시지 원문은 본문에 쓰지 않는다. 면접관은 커밋 세부 기록까지 보지 않는다.
  - 근거가 저장소 이력뿐인 주장에는 `(이력: report N)`만 붙인다. N은 report 파일의 항목 번호다.
  - 해시, 날짜, 메시지, 커밋 수·비율 같은 통계는 report 파일에 모은다.
  - 코드 근거(파일:줄), 정리글·PDF·작업 기록 근거는 본문에 그대로 둔다.
- 코드 스니펫은 핵심 로직만 선별한다. 각 스니펫에 (Why) 주석이나 설명을 붙인다. 예외 처리 경로도 보여준다.
- Trade-off는 대안을 최소 2개 비교한다. 각각 장점·단점과 결정 이유를 쓴다. 저장소에 대안의 흔적이 없으면 정리글에서 찾는다. 둘 다 없으면 [확인 필요]로 질문을 남긴다.
- 기술 스택 나열로 끝내지 않는다. 구조를 그렇게 나눈 이유를 함께 쓴다.

## 출력 형식
- 결과는 Markdown 파일 두 개다: {출력 폴더}/tech-doc-source.md, {출력 폴더}/tech-doc-source-report.md
- 사용자가 바로 손으로 고칠 수 있게 쓴다.
  - 본문은 일반 문단과 글머리표로 쓴다. 인용 블록(>)으로 본문 전체를 감싸지 않는다.
  - HTML, 복잡한 중첩, 과도한 표를 쓰지 않는다. 표는 클래스 역할 분담처럼 표가 꼭 필요한 곳에만 쓴다.
- 레이아웃을 따로 나눠야 하는 것만 블록으로 분리한다.
  - 코드: ```csharp 등 언어 태그를 붙인 코드 블록
  - 다이어그램: ```mermaid 블록(flowchart, classDiagram, sequenceDiagram 중 적합한 것)
  - 블록 바로 위에 한 줄 제목을 둔다. 예: [다이어그램] 전투 처리 시퀀스
- 섹션 헤더는 틀의 5단 구조 번호와 이름을 그대로 쓴다. 유형 B/C면 틀의 변형 구조를 따른다.
- 문서 맨 앞에 "작성 메모" 섹션을 둔다. 고른 문서 유형과 이유, 섹션별로 다룬 핵심 기능, Trade-off 후보, 다이어그램 종류를 적는다. 사용자가 목차를 검토할 때 이 메모를 본다.

## 표기 규칙 (개인 정리글 대조)
본문 문장 바로 아래에 다음 태그 줄을 단다. 태그는 검색·삭제하기 쉽게 줄 맨 앞에 둔다.
- [개인노트 일치] 정리글과 내용이 같다. 형식: [개인노트 일치] personal_source/…/파일명 — "정리글 원문 짧은 인용"
- [개인노트 보강] 정리글의 느낌·고민을 이 문장에 녹였다. 원문 인용을 붙인다.
- [개인노트 불일치] 정리글과 저장소 코드가 다르다. 양쪽 근거를 모두 적는다.
- [확인 필요] 근거가 부족하다. 사용자가 답할 질문을 한 줄로 적는다.
- [측정 필요] 수치가 필요한데 데이터가 없다. 무엇을 어떻게 재면 되는지 적는다.
정리글이 "없음"인 프로젝트는 개인노트 태그를 쓰지 않는다.

## 문서 끝에 붙일 것
1. 근거 파일 목록: 실제로 읽은 저장소 파일과 정리글 파일(PDF·zip·json·csv 포함, 읽은 쪽·범위 표시). 커밋 목록은 넣지 않고 report에 둔다.
2. 정리글에서 쓰지 않은 내용: 쓰지 않은 이유를 한 줄씩
3. 피드백 요청 질문: 사용자가 답하면 문서가 깊어지는 질문 5~10개(Why, 대안, 수치, 트러블슈팅 위주)

## report 파일 (tech-doc-source-report.md)
본문이 `(이력: report N)`으로 가리키는 근거와 작업 기록을 모은다. 면접관용이 아니라 사용자가 근거를 다시 찾을 때 보는 메모다.
1. 이번 실행에서 읽은 자료와 방법: 0단계에서 고른 파일, PDF를 읽은 방법과 쪽, zip 안 파일과 저장소 비교 결과, 중복 파일
2. 본문이 가리키는 커밋 근거: 항목 번호별로 해시, 날짜, 메시지, 그 커밋이 보여 주는 것
3. 커밋 통계: 기간, 계정별 커밋 수, 본인 커밋 수, 파일별 본인 비율, 변경량, 태그
4. 자료 사이의 불일치: 본문의 [개인노트 불일치]·[확인 필요]와 연결되는 것
5. 본문에서 뺀 후보: 커밋만 근거라 본문에 넣지 않은 트러블슈팅 후보 등

# 금지 사항
- repos 와 personal_source 안의 파일을 수정하지 않는다. 쓰기는 {출력 폴더}/tech-doc-source.md 와 {출력 폴더}/tech-doc-source-report.md 에만 한다. zip 풀기·PDF 렌더링·임시 스크립트는 %TEMP% 아래 임시 폴더에만 둔다.
- repos 안의 git 상태를 바꾸지 않는다(checkout, fetch, pull, reset, stash 등 금지). log, show, shortlog, diff 같은 읽기 명령만 쓴다.
- 한 세션에서 프로젝트를 2개 이상 처리하지 않는다.
- 새 세션을 직접 띄우지 않는다.
- 빌드, Unity 실행, 패키지 설치를 하지 않는다.
- git commit, push 를 하지 않는다.
