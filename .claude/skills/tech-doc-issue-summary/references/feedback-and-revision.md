# 문서가 나온 뒤 — 퇴고와 외부 피드백 반영

출처: 2026-11-17~11-27 세션. WGO 퇴고·1장 개편·5장 구조 개편·장 연결 강화(11-17), Mini FTL 개편안 섞기(11-19), `/portfolio-check` 루프(11-19), 외부 피드백 반영 계획 1~14차(11-21~22, `report/피드백-반영-계획.md`), WGO 1~3장 연결성 개선(11-26, `report/WGO/2026-11-26-1-3장-연결성-개선-계획.md`), 2장 협업 파트 재구성(11-26). 회고: `dev-growth/retros/2026/2026-11-22_portfolio-test_wgo-피드백-반영-gantt-1.3.md`·`2026-11-26_portfolio-test_wgo-1-3장-연결성.md`.

고민 분류 7단계로 문서에 넣은 뒤에도 문서는 여러 번 바뀝니다. 바뀌는 계기는 셋입니다: 사용자가 직접 쓴 새 초안, 문서 전체 흐름 손보기, 멘토·강사 같은 외부 피드백. 어느 경우든 **사용자 문서를 대신 쓰지 않는다**(루트 `CLAUDE.md` 원칙 2)는 같습니다. 사용자가 "고쳐 줘"·"섞어 봐"라고 한 범위만 옮기고 다듬습니다.

## 1. 새 초안을 기존 문서와 섞기

사용자나 다른 AI가 쓴 개편 초안을 받으면 **통째로 바꾸지 않습니다.**

- 실패 사례(Mini FTL 11-19): 예약 작업이 개편 초안으로 문서를 통째로 교체했습니다(1394줄 → 359줄). 사용자: "권고안대로 다 바꾸는 게 아니라 어떻게 혼합할지 계획… 1. 개요는 기존 걸 살리되…, 3은 최대한 유지". 되돌린 뒤 섞어 512줄이 됐습니다.
- 순서:
  1. 장마다 "기존 유지 / 개편안 / 둘을 합침" 중 무엇인지 사용자와 목차를 먼저 정합니다(계획만, 글은 아직).
  2. 정한 목차대로 옮깁니다. 지우는 원문은 `backup/<폴더>/`나 `_intake/`에 원문 그대로 남깁니다.
  3. report 작업 파일에 「새 목차」(장마다 어디서 왔는지)와 「확인해 주세요」(Claude가 줄이거나 새로 쓴 문장마다 한 줄)를 씁니다.
- 섞다가 지침 위반 문장("A가 아니라 B", 제3자 시점 "제작자의 회고")이 보이면 뜻을 유지한 채 고치고 「확인해 주세요」에 남깁니다.
- 섞을 때 함께 받은 교정(같은 세션): "그림 그대로 넣지 말고 WGO처럼 핵심 루프만", "인사담당자·팀장이 보면 소개, 왜 만들었나 다음에 갑자기 시스템이 나오면?", "'제작자의 회고' 이런 걸 넣으면 안 돼. 발표·설명하는 입장". 이 셋은 지금 `portfolio-writing.md` 「글쓰기 기본 지침」과 규칙 7에 들어 있습니다.

## 2. 흐름 손보기 (장 구조·장 연결)

- **"다시 쓰기"가 아니라 "전개 흐름 계획"을 먼저 냅니다.** 사용자 요청 원문: "모든 내용을 다시 쓰는 게 아니라 전개 흐름 계획". 계획은 옛 절이 어디로 가는지 표(옛 위치 → 새 위치 → 바뀌는 문장 수)로 냅니다.
- **장 연결 강화:** 각 장 첫 문장이 앞 장 마지막 주장을 받는지 봅니다. 끊기는 곳을 `위치 | 끊기는 이유` 표로 먼저 보여 주고(분석), 고칠 안을 D-번호 절로 나눠 씁니다(초안). 질문은 메인 report 목록 한 곳에만 두고 각 질문에 `[[#D-n. …]]` 링크를 겁니다.
- **사용자가 개선 프롬프트를 직접 써서 줄 때**(11-26 1~3장, 2장 협업): 프롬프트를 그대로 실행하지 말고 ① 현재 분석 ② 바꿀 안(D-번호) ③ 질문 ④ 초안 순서로 report를 냅니다. 원본 문서는 사용자가 "이 초안대로 반영해"라고 한 뒤에 고칩니다.
- 큰 개편은 워크트리에서 합니다. report도 워크트리 안에 쓰고, 끝나면 메인 트리 `report/`로 옮기고 목차를 갱신합니다.
- 말투 일괄 전환(예: 한다체 → 합니다체)은 프로젝트 문서와 슬라이드 글을 함께 바꾸고, 인용(`>`)·코드·다이어그램 라벨·제목은 그대로 둡니다. 바꾼 뒤 `tools/voice-lint.py`로 남은 한다체를 찾습니다.

## 3. 외부 피드백 반영 계획 (차수식)

멘토·강사가 준 피드백 문서 하나가 여러 프로젝트에 걸칠 때 씁니다. 견본은 `templates/feedback-plan.md`입니다.

### 계획 파일 구조

1. **맨 위 「★ 지금 확인할 것」** — 사용자가 이번 차수에 답할 것과 방금 확정된 것만. 지난 차수는 아래로 내립니다.
2. **0. 한눈에** — 프로젝트마다 **"역할" 한 줄**을 먼저 고정합니다. 이 역할이 피드백 전체의 판정 기준입니다. 예: WGO = 기획·PM·협업, Hive = 엔지니어링, Mini FTL = 첫 개발의 삽질과 학습.
3. **1. 우선순위 표** `순위 | 프로젝트 | 할 일 | 이유 | 크기(대·중·소)`. 순서 기준: ① 목차가 바뀌는 일 ② 피드백이 지적한 그림 ③ 사진 ④ "+추가"는 맨 뒤.
4. **2. 프로젝트별 목차안과 구체화할 것** — 프로젝트마다 W-1·H-1·F-1 같은 번호로 할 일을 나누고, 사용자 답이 필요한 줄 아래에 빈 답 줄을 둡니다.
5. **3. 반영 방법(진행 순서)** — 결정 답 받기 → "고쳐 줘" 범위만 옮기기(새 사실 없음) → 그림은 `format/03-diagrams.md`로 실제 코드 이름 초안 → 확인 → 문서에 넣기 → 프로젝트마다 `/portfolio-build` → `deck-edits.py`·`portfolio-edits.py apply --all` → 마지막에 `/portfolio-check`.
6. **4. 먼저 정할 결정 D1~Dn** — 피드백이 레포 규칙과 부딪히는 곳(예: "4·5장을 스프린트 2파트로" ↔ "5장 구조 고정")을 안 A/안 B로 묻습니다.
7. **5~. 차수별 답 반영** — 「정해진 것」·「보류·삭제한 것」·「원천 재확인」을 차수마다 덧붙입니다.

### 진행하며 배운 것

- **피드백 문장을 Claude 식으로 넓게 읽지 않습니다.** D1에 사용자 답: "전혀 이런 말이 아니고 내용 위치랑 글 내용만 조금만 다듬어서 … 특정 기점 이전, 이후 이렇게 나뉘어서 읽는 사람이 명쾌하게 읽히게". 피드백 해석이 둘 이상이면 가장 작은 변경안을 첫 안으로 둡니다.
- **질문은 예시를 들어 묻습니다.** 사용자: "뭔말임 정확히 예시를 들어서 설명해야지 내가 답변할 수 있어."(D3 번호 체계) Claude가 답 없이 정할 수 있는 것(D3처럼 나중에 고치면 되는 것)은 Claude가 정하고 이유를 적습니다.
- **피드백이 그린 그림을 그대로 옮기지 않습니다.** 인과 관계가 맞는지 먼저 검토합니다(11-22 WGO 1.3 플로우차트가 사용자 프롬프트로 전면 개편됨).
- **맥락 없는 구절을 옮기지 않습니다.** 사용자가 "회복 중 반격"에 "어디서 나온 거냐"고 물은 사례. 옮기는 구절마다 원천 위치를 report에 둡니다.
- **사실은 원천 날짜로 확인합니다.** 사용자: "9월 11일 발표인데 왜 14일까지?", "3·4차 스프린트 주기 틀림". 일정·기간 문장은 Asana CSV·발표 PDF를 다시 열어 확인합니다(W-D·W-E 정정).
- **사실 확인 질문은 주장 하나씩** 묻습니다(backlog B-008). 여러 주장을 한 질문에 묶으면 사용자가 어느 것에 답하는지 흐려집니다.
- **그림은 실제 화면에서 봅니다.** `doc.html` 컨테이너 안에서 gantt가 300px로 작아진 사례. Mermaid는 상세 문서·슬라이드 둘 다 렌더 확인합니다.
- **"보완 요소"는 문서에서 지우지 말고** 채용 담당자에게 말하는 「아쉬운 점」 문장으로 바꿉니다.
- 차수가 쌓이면 진척을 피드백 받은 날과 비교해 달라는 요청이 옵니다("금요일 피드백 받았을 때와 대비해서 … 얼마나 달라졌는지"). 「한눈에」에 순위별 ✅·△를 유지해 두면 바로 답할 수 있습니다.

## 4. `/portfolio-check` 루프

- 위치: 반영이 끝난 뒤 마지막 점검입니다. 결과는 루트 `report.md`에 생기므로 `.claude/CLAUDE.md` 「스킬이 루트 report.md를 덮어쓸 때」대로 프로젝트 작업 파일로 옮깁니다.
- 결과 처리: 필수·권장·참고 줄마다 사용자 답을 받아 반영합니다. "재료 점검표" 부족 칸은 촬영 요청이나 ✍ 리마인드 할 일로 넘깁니다.
- 점검이 초안 문단(예: 「목표한 경험 돌아보기」)을 제안하면 문서에 넣지 않고 report에만 둡니다. 사용자가 채웁니다.

## 5. 세션 나누기 (이 단계)

- 퇴고와 빌드는 다른 세션입니다. 사용자: "먼저 압축하고 새 세션 열어서 Opus 높음으로 빌드".
- 프로젝트가 바뀌면 새 세션입니다. 사용자: "hive랑 쓰는 자료 다르니까 새 세션".
- 세션을 끝낼 때 다음 세션 시작 프롬프트를 report에 남깁니다(예: "report.md 요약판부터 읽고 이어서 …").
- 같은 시각에 여러 일을 하려면 예약 작업으로 요청마다 세션을 나눕니다. 예약 작업에는 "계획 짜지 말고 프롬프트 전체를 예약"처럼 실행 지시를 그대로 넣고, "`git diff`로 사용자 미커밋 수정 줄을 확인한 뒤 건드리지 않음"을 꼭 넣습니다.
