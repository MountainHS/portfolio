# 프로젝트 기술적 고민 원본 자료 분류 및 기술문서 정리 계획 수립

## 1. 역할과 최종 목적

당신은 현재 프로젝트 폴더 전체에 접근할 수 있는 **기술문서 분석 및 정리 에이전트**다.

이번 작업의 목적은 완성된 기술문서를 만드는 것이 아니다.

**프로젝트에 쌓인 원본 자료(Raw Data)에서 개발자의 고민, 판단, 시행착오, 설계 변경 과정을 빠짐없이 발굴하고, 이를 체계적으로 정리하기 위한 계획을 수립하는 것**이다.

기존에 AI를 사용해 기술문서를 작성하면 다음 문제가 반복되었다.

- 개발자가 실제로 고민했던 내용이 사라진다.
- 왜 특정 방법을 선택했는지보다 최종 구현 방식이 강조된다.
- 실패한 시도와 검토했지만 채택하지 않은 대안이 누락된다.
- 처음 생각과 개발 후 판단이 달라졌어도 최종 결과만 남는다.
- AI와 함께 문제를 해결했다면 초기 프롬프트, 생성 결과, 문제 발견, 재시도 과정이 사라진다.
- 문서가 깔끔해지는 대신 개발자의 사고 과정과 기술적 의사결정이 보이지 않는다.

**이러한 정보 손실을 막는 것이 이번 작업의 최우선 목표다.**

코드 구조나 구현 기술을 설명하는 것보다, 그 기술을 선택하고 변경한 이유를 복원하는 데 집중하라.

## 2. 작업 범위와 제약

### 조사 대상

현재 프로젝트 폴더에 존재하거나 접근할 수 있는 관련 자료를 조사하라.

예를 들면 다음과 같다.

- 개발 당시 작성한 고민과 메모
- 기술문서 초안 및 완성본
- 프로젝트 기획 및 설계 문서
- 구현 계획 및 TODO 기록
- 문제 해결 및 디버깅 기록
- 회고 및 피드백 문서
- AI에 전달했던 프롬프트와 응답 기록
- Git 커밋, 브랜치, PR, 이슈
- 소스 코드와 주석
- 테스트 결과 및 성능 측정 자료
- 기타 기술적 판단을 확인할 수 있는 자료

**문서만 분석하지 말고 필요할 때 코드와 Git 이력도 함께 확인하라.**

다만 코드가 현재 어떤 구조인지를 확인하는 것과, 개발자가 왜 그렇게 설계했는지를 확인하는 것은 별개의 작업이다.

현재 코드만으로 당시의 판단을 추측하지 마라.

### 작업 제약

1. 기존 파일을 수정하거나 삭제하지 마라.
2. 완성된 기술문서를 작성하지 마라.
3. 원본을 재작성하거나 요약하는 과정에서 고민을 임의로 제거하지 마라.
4. 자료에 없는 개발자의 의도나 생각을 만들어내지 마라.
5. 불명확한 내용은 추론으로 확정하지 말고 확인 필요 사항으로 표시하라.
6. 현재 구현이 이전 설계보다 우수하다고 단정하지 마라.
7. 동일한 고민을 다룬 자료가 여러 개라면 통합할 수 있지만, 원본 출처는 모두 유지하라.
8. 원본 자료가 많다고 해서 주요 고민을 임의로 생략하지 마라.

최종 결과물은 **1차 분류 및 정리 결과 + 출처 대응 관계 + 사용자 검토 항목 + 이후 정리 계획**이다.

## 3. 1단계 — 원본 자료 조사 및 고민 발굴

먼저 프로젝트 자료 전체를 조사하고, 기술적 고민이 포함된 내용을 발굴하라.

### 발굴 기준

다음과 같은 내용은 모두 기록할 가치가 있다.

- 어떤 문제가 발생했는가?
- 처음에는 무엇이 문제라고 생각했는가?
- 왜 그 방법을 선택했는가?
- 다른 해결 방법을 고민했는가?
- 어떤 제약 때문에 특정 방법을 포기했는가?
- 처음 생각한 방법이 예상대로 작동했는가?
- 어떤 문제가 새롭게 발생했는가?
- 왜 기존 설계를 수정했는가?
- AI에게 무엇을 요청했고, 그 결과를 어떻게 평가했는가?
- 해결하지 못한 문제나 미래에 개선하려던 내용이 있는가?
- 개발 당시와 현재의 판단이 달라졌는가?

특히 다음 내용을 놓치지 마라.

**최종 구현에 반영되지 않았더라도 개발자의 판단 과정에 영향을 준 고민은 보존해야 한다.**

예를 들어:

- 고려했다가 포기한 아키텍처
- 실제 구현하지 못한 개선안
- 테스트했지만 효과가 없었던 최적화
- 일정 문제로 선택한 임시 해결책
- AI에게 잘못 요청해 발생한 문제
- 팀원과 협업하면서 발견한 설계상의 문제

### 발굴 결과

고민마다 고유 ID를 부여하라.

예시:

- D-001: 네트워크 메시지 처리 구조에 대한 고민
- D-002: 다수 몬스터의 목표 위치 선정
- D-003: 특정 버그를 해결하기 위한 AI 프롬프트 수정

ID는 이후 모든 표와 정리 결과에서 동일하게 유지한다.

하나의 고민이 여러 문서에 나타나면 가급적 하나의 ID로 묶되, 서로 다른 판단이나 문제를 지나치게 합치지 마라.

## 4. 2단계 — 고민을 세 가지 수준으로 분류

발굴한 고민을 아래 기준으로 분류하라.

### Level 1 — Micro Decision Log

작은 기술적 판단이나 비교적 단순한 문제 해결 기록.

예시:

- 특정 API를 선택한 이유
- 간단한 코드 구조 변경
- 작은 버그 수정 과정
- 단일 AI 프롬프트를 통한 문제 해결
- 기존 구현에 사소한 조건을 추가한 이유

기록할 핵심 정보:

1. 문제 상황
2. 선택한 방법과 판단 이유
3. 적용 결과
4. 남은 문제 또는 배운 점

작은 고민이라도 판단 과정이 있다면 버리지 마라.

### Level 2 — Technical Decision & Iteration Log

여러 대안이나 시행착오를 동반한 의미 있는 기술적 의사결정.

예시:

- 시스템 아키텍처 선택
- 상태 머신 구조 설계
- 네트워크 동기화 방식 결정
- AI를 반복 사용하며 설계 개선
- 복잡한 버그의 원인 분석과 해결
- 성능 개선을 위한 여러 방식의 비교
- 반복적인 리팩토링 과정

기록할 핵심 정보:

1. 문제 상황 및 목표
2. 제약 조건
3. 고려한 대안
4. 최초 판단과 선택 이유
5. 적용한 방법
6. 예상과 실제 결과
7. 실패 및 새로운 문제
8. 판단 변경과 재시도
9. 최종 결과의 장단점
10. 개선 방향과 배운 점

**시행착오가 여러 차례 있었다면 시도별로 구분해서 보존해야 한다.**

### Level 3 — Portfolio Case Study 후보

프로젝트의 핵심적인 기술적 역량을 보여줄 수 있는 대표 사례.

예시:

- 프로젝트에서 가장 중요한 시스템의 설계와 개선
- 기술적 난도가 높았던 문제 해결
- 여러 제약 사이에서 명확한 판단 기준을 세운 사례
- 실제 측정과 검증을 통해 설계를 개선한 사례
- 실패 이후 설계를 크게 수정한 사례
- 협업 전체에 영향을 준 기술적 결정

기록할 핵심 정보:

1. 문제의 중요성과 프로젝트 맥락
2. 개발자가 직접 내린 기술적 판단
3. 대안과 선택 근거
4. 중요한 시행착오와 설계 변경
5. 구현 결과와 검증 자료
6. 장단점 및 개선 방향
7. 포트폴리오에서 강조할 수 있는 기술적 역량

### 분류 시 주의사항

- Level 3는 단순히 Level 2보다 기술 난도가 높은 항목을 의미하지 않는다. **포트폴리오의 대표 사례로 발전시킬 가치가 있는 항목**이다.
- Level 3로 분류해도 Level 2 수준의 상세한 원본 기록은 보존해야 한다.
- 현재 기준에서 중요하지 않아 보인다는 이유로 Level 1 고민을 삭제하지 마라.
- 분류가 모호하면 임시 수준과 판단 근거를 기록하고 사용자 검토 대상으로 남겨라.
- 문서의 길이와 코드의 복잡도만으로 수준을 판단하지 마라.

## 5. 3단계 — 수준별 1차 정리

분류 결과를 바탕으로 각 고민을 1차 정리하라.

**이 단계에서 가장 중요한 요구사항은 원본 내용과 정리된 내용의 대응 관계를 사용자가 직접 검증할 수 있어야 한다는 것이다.**

### 모든 항목의 공통 구조

각 고민은 다음과 같이 정리하라.

#### D-XXX. [고민 제목]

**분류:** Level 1 / Level 2 / Level 3
**분류 이유:**
**자료 충실도:** 충분 / 일부 부족 / 자료 부족

#### A. 현재 파악한 고민의 흐름

원본에서 확인되는 내용을 시간순 또는 논리적 순서로 정리하라.

- 최초 문제
- 최초 판단
- 선택한 방법
- 적용 및 시행착오
- 판단의 변경
- 현재 결과
- 향후 개선 방향

단, 원본에서 확인할 수 없는 단계는 억지로 채우지 마라.

특히 Level 1은 간결하게 작성하고, Level 2와 Level 3는 검토한 대안과 반복적인 시도를 충분히 설명하라.

#### B. 원본과 정리 내용의 대응표

다음 형태를 사용하라.

| 단계    | 1차 정리 내용 | 원본 위치        | 원본 핵심 내용 | 대응 상태 |
| ----- | -------- | ------------ | -------- | ----- |
| 문제 상황 | ...      | 파일 경로 및 줄 번호 | 원문 발췌    | 명확    |
| 최초 판단 | ...      | 파일 경로 및 줄 번호 | 원문 발췌    | 명확    |
| 선택 이유 | ...      | 파일 경로 및 줄 번호 | 원문 발췌    | 일부    |
| 적용 과정 | ...      | 코드 또는 문서 위치  | 원문 발췌    | 명확    |
| 결과    | ...      | 테스트 또는 문서 위치 | 원문 발췌    | 불명확   |
| 개선 방향 | ...      | 메모 위치        | 원문 발췌    | 명확    |

**원본 위치는 가능한 한 파일 경로와 줄 번호, Markdown 제목, 커밋 해시 또는 기타 재확인 가능한 식별자로 표시하라.**

원본 핵심 내용은 실제 원문의 일부를 그대로 발췌한다.

발췌문만으로 의미를 알기 어려우면 주변 문맥도 함께 제공한다.

대응 상태는 다음 중 하나로 표시한다.

- **명확:** 정리한 내용이 원본에 직접적으로 존재함
- **일부:** 여러 근거를 조합해야 하거나 일부만 확인됨
- **추론:** 원본에 직접적인 설명이 없으며 정리가 해석에 의존함
- **미확인:** 이를 뒷받침하는 근거를 찾지 못함

추론 내용은 확인된 사실과 문장 수준에서도 구분하라.

#### C. 누락 및 손실 점검

정리하면서 다음 사항을 확인하라.

- 정리하지 않은 원본 고민이 있는가?
- 고려했지만 선택하지 않은 대안이 사라졌는가?
- 실패하거나 폐기된 방법이 누락되었는가?
- AI 프롬프트 변경 과정이 사라졌는가?
- 다른 문서와 모순되는 내용이 있는가?
- 최종 코드만 보고 추정한 내용을 사실처럼 기술했는가?
- 최초 설계와 최종 구현의 차이가 드러나는가?
- 원본에서는 중요하게 언급했지만 1차 정리에서 축소된 내용이 있는가?

발견한 항목은 삭제하거나 임의로 해결하지 말고 별도로 기록하라.

#### D. 추가 확인이 필요한 질문

현재 자료만으로 복원하기 어려운 정보가 있다면 개발자에게 확인할 질문을 작성하라.

예:

- 당시 A 방식 대신 B 방식을 선택한 가장 중요한 이유가 무엇이었는가?
- 최초 설계를 변경한 직접적인 계기는 무엇이었는가?
- 해당 방법의 성능 개선 효과를 실제로 측정했는가?
- AI가 생성한 코드 중 직접 수정한 부분은 어디인가?

질문은 원본을 분석해도 확인되지 않는 내용에 한정하라.

---

## 6. 4단계 — 전체 분류 결과와 자료 보존 상태 확인

개별 고민의 1차 정리가 끝나면 전체 목록을 제공하라.

### A. 고민 분류 목록

| ID    | 고민 제목 | 분류 | 주요 원본 | 자료 충실도 | 사용자 검토 필요 |
| ----- | ----- | -- | ----- | ------ | --------- |
| D-001 | ...   | L2 | ...   | 충분     | 아니요       |
| D-002 | ...   | L3 | ...   | 일부 부족  | 예         |
| D-003 | ...   | L1 | ...   | 충분     | 아니요       |

### B. 원본 자료 커버리지

| 원본 파일 또는 자료 | 발굴한 고민 ID    | 반영 여부 | 아직 정리되지 않은 내용 |
| ----------- | ------------ | ----- | ------------- |
| ...         | D-001, D-004 | 반영    | 없음            |
| ...         | D-002        | 부분 반영 | 과거 개선안        |

핵심은 두 방향의 검증이 가능해야 한다는 것이다.

1. **고민 → 원본:** 정리된 주장이 실제 어떤 자료에서 나왔는지 찾을 수 있어야 한다.
2. **원본 → 고민:** 원본 자료의 중요한 고민이 어디에 반영되었는지 찾을 수 있어야 한다.

특히 두 번째 방향의 검증을 생략하지 마라.

원본에 존재하는 고민이 어떤 정리 항목에도 대응하지 않는다면 누락된 것으로 표시하라.

---

## 7. 5단계 — 사용자 검토를 위한 피드백 제안

1차 정리 결과를 바탕으로 사용자가 무엇을 검토해야 하는지 제안하라.

검토 항목은 다음 기준으로 정렬한다.

**우선순위 높음**

- 중요한 고민인데 최초 판단 근거가 부족한 경우
- 원본과 정리한 내용 사이에 의미 차이가 있는 경우
- 서로 모순되는 자료가 있는 경우
- 주요 시행착오가 누락되었을 가능성이 있는 경우
- Level 2 또는 Level 3의 분류가 애매한 경우

**우선순위 보통**

- 추가 검증 결과가 필요한 경우
- 구현 결과는 있지만 개선 방향이 없는 경우
- 여러 고민을 하나로 묶을지 결정해야 하는 경우

**우선순위 낮음**

- 표현 개선
- 제목 개선
- 세부 코드 설명 보완
- 문서 디자인 및 레이아웃

지금은 문장 완성도보다 **원본 고민의 보존 여부와 분류 정확성**을 먼저 확인해야 한다.

각 항목에 대해 다음을 제시하라.

- 대상 고민 ID
- 발견한 문제
- 관련 원본
- 권장 정리 방향
- 사용자에게 확인받을 내용

---

## 8. 6단계 — 기술문서 원본 자료 정리 계획 수립

1차 정리 결과를 바탕으로 이후 작업 계획을 작성하라.

여기서 말하는 기술문서 원본 자료란 완성된 포트폴리오 문서가 아니라, **향후 기술문서를 만들 때 사용할 신뢰할 수 있는 기술적 고민과 판단의 기록**을 의미한다.

계획은 다음 순서로 구성하라.

### 단계 A. 원본 내용 보존 및 분류 수정

- 현재 어떤 자료를 보존해야 하는가?
- 서로 중복되는 내용은 무엇인가?
- 동일한 고민의 다른 시점 기록을 어떻게 연결할 것인가?
- Level 1·2·3 분류를 어떻게 조정할 것인가?

### 단계 B. 고민별 판단 과정 정리

- 각 고민에서 어떤 판단 단계를 복원해야 하는가?
- 시행착오를 어떤 단위로 나누어야 하는가?
- 원본의 문장을 유지할 부분과 설명을 보완할 부분은 무엇인가?
- AI 관련 기록을 어떤 형식으로 연결할 것인가?

### 단계 C. 누락된 근거 보강

- 무엇을 개발자에게 직접 질문해야 하는가?
- 무엇을 코드 및 Git 이력에서 확인할 수 있는가?
- 어떤 테스트 또는 측정이 추가로 필요한가?
- 확인이 불가능한 과거 사실을 어떻게 표시할 것인가?

### 단계 D. 기술문서 원본 자료 구조 제안

- 고민별 문서를 어떻게 나눌 것인가?
- 공통 Markdown 템플릿은 무엇을 사용할 것인가?
- 원본과 정리본의 연결을 어떻게 유지할 것인가?
- 이후 내용을 추가할 때 어떻게 변경 이력을 보존할 것인가?

### 단계 E. 포트폴리오 활용 계획

- Level 3 후보 중 어떤 사례가 가장 적합한가?
- 각 사례에서 보여줄 수 있는 기술적 역량은 무엇인가?
- 어떤 구현 결과와 검증 자료가 필요한가?
- 현재 자료만으로 설명할 수 없는 부분은 무엇인가?

**이 단계에서는 계획만 작성하라. 사용자 피드백을 받기 전에는 파일 구조를 변경하거나 문서를 재작성하지 마라.**

## 9. 최종 결과물의 출력 순서

다음 순서로 결과를 보고하라.

1. **전체 조사 개요**

   - 조사한 자료 범위
   - 발굴한 고민 수
   - Level별 분류 결과
   - 조사하지 못한 자료와 이유

2. **전체 고민 분류 목록**

   - 고유 ID
   - 고민 제목
   - Level
   - 분류 이유
   - 원본 위치
   - 자료 충실도

3. **고민별 1차 정리**

   - 현재 파악한 사고 및 의사결정 흐름
   - 원본과 정리 내용의 대응표
   - 보존해야 할 내용
   - 누락 및 충돌 사항
   - 추가 확인 질문

4. **원본 자료 커버리지 검사**

   - 원본별 대응 고민
   - 누락 또는 미반영 내용

5. **사용자 검토 요청 사항**

   - 중요도순으로 정렬
   - 확인이 필요한 이유와 근거 명시

6. **향후 기술문서 원본 자료 정리 계획**

   - 실제 작업 순서
   - 수정 및 보완 대상
   - 자료 보존 방식
   - 예상되는 문제
   - 사용자 피드백을 반영해야 할 결정

자료가 매우 많다면 결과를 고민 ID 기준으로 여러 묶음으로 나누어 제시해도 된다. 단, 각 묶음에 포함된 범위와 아직 처리하지 못한 자료를 명확히 표시해야 한다.

**충분히 조사하지 못한 자료까지 모두 확인했다고 보고해서는 안 된다.**

## 10. 반드시 지켜야 할 최종 원칙

이번 작업의 성공 기준은 문서가 읽기 좋게 정리되었는지가 아니다.

다음 다섯 가지다.

1. 원본에 존재했던 중요한 고민이 사라지지 않았는가?
2. 개발자의 최초 판단과 이후 판단 변화가 구분되는가?
3. 정리된 내용이 원본의 어디에서 왔는지 확인할 수 있는가?
4. 원본에 없는 내용을 AI가 임의로 보충하지 않았는가?
5. 사용자가 1차 정리 결과를 보고 분류 및 정리 방향에 대해 구체적으로 피드백할 수 있는가?

**최종 구현보다 그 구현에 도달하기까지의 사고 과정이 이번 작업의 핵심 자료다.**

원본의 불완전한 문장, 실패한 생각, 모순된 판단, 해결되지 않은 고민까지 중요한 기록으로 취급하라.

이번 단계에서는 반드시 **1차 정리 및 정리 계획 수립까지만 수행**하고, 실제 기술문서 원본 자료의 재작성은 사용자 피드백 이후로 남겨두어라.
