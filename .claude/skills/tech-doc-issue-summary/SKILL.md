## 0단계 — 가드와 모드 판정

1. **가드.** 다음이 모두 맞을 때만 진행합니다. 하나라도 아니면 아무 파일도 만들지 않고, 이 스킬은 기술 문서 소스 작업용이라는 점과 `/tech-doc-issue-summary <src 폴더>` 쓰는 법만 알립니다.
   - 첫 인자가 `src/` 바로 아래 폴더 이름이고, `_`로 시작하지 않습니다.
   - 그 폴더에 기술 문서 `.md` 또는 `_intake/`가 있습니다.
2. **이름 정하기.** 분류 파일은 `report/고민-분류/<src 폴더>.md`(WGO는 예전 이름 `WGO.md` 그대로), ID 접두어는 `INDEX.md`의 공통 규칙(`WGO`·`HP`·`FTL`)을 따르고, 없으면 사용자에게 한 번 묻습니다. 별칭표는 `report/고민-분류/<접두어>-alias.tsv`.
3. **모드.** 인자에 모드가 있으면 그것을 씁니다. 없으면:

| 상태 | 모드 |
|---|---|
| 분류 파일이 없음 | 시작(1~4단계) |
| 분류 파일에 탭으로 들여쓴 답 줄이 있음 | 답 반영(5단계) |
| 인자나 요청에 `Q-번호`와 "대화·티키타카" | 대화 세션(6단계) |
| "기술 문서에 반영" 요청 | 기술 문서 반영(7단계) |

## 1단계 — 원천 범위 확인 (시작 모드, 반드시 사용자 확인)

- 원천 후보를 찾습니다: `INDEX.md`의 원천 폴더 칸, `src/<폴더>/_intake/`, `report/<폴더>.md`, 노트·일지 폴더, 코드 레포, Git 이력, 대화 기록.
- 후보를 묶어 AskUserQuestion으로 고르게 합니다. 묶음마다 무엇이 들었는지(파일 수·성격)를 설명에 씁니다.
- **고르지 않은 자료는 보지 않습니다.** 코드·Git·블로그·다른 report는 사용자 답이 가리킨 범위만 나중에 봅니다. 코드가 크면 사용자가 "이 소스 참고해"라고 짚은 곳만 보고, 대신 질문으로 역질문을 유도합니다.
- 확정한 범위는 분류 파일 §5 「조사한 자료 / 조사하지 못한 자료와 이유」와 `INDEX.md` 진행 상태 행에 적습니다.
- 이미 다른 세션이 범위를 확정해 브리프로 넘겼으면 다시 묻지 않고 기록만 합니다.

## 2단계 — 원천 조사

- md5로 같은 파일을 찾아 한 번만 읽고, §8 단계 A에 중복을 적습니다.
- **md 원천은 메인 세션이 직접 정독합니다.** 충실도가 핵심이라 위임하지 않습니다. 읽으면서 `별칭:L줄 + “원문 발췌”`를 바로 적습니다.
- 큰 CSV·json·PDF는 Explore 하나에 맡깁니다. 브리프: "고민 단서마다 파일 + 위치(줄·gid·쪽) + 원문 그대로만 돌려줘. 해석·요약 금지. 못 읽은 범위와 키워드 거르기로 놓쳤을 수 있는 범위를 따로 적어." 돌아온 인용 줄은 메인 세션이 grep으로 다시 확인합니다.
- 별칭표를 만듭니다: 본인 회고·메모는 `R1`…, Asana는 `CSV`, 발표는 `PDF발표`, 현재 기술 문서는 `TD`. 위치는 `` `R2:L86-92` ``, PDF는 `PDF발표 p14`. 별칭 → 절대경로를 TSV로 저장합니다(검사 스크립트 입력).
- 개인정보(팀원 이메일·ssh 키 등)는 옮기지 않습니다. 팀원 담당 작업은 정리 대상에서 빼고, 뺀 사실은 §7 커버리지에 적습니다.

## 3단계 — 발굴과 분류

- [references/levels.md](references/levels.md)의 발굴 기준으로 고민을 찾고 ID `<접두어>-D-001`부터 붙입니다. 한 번 붙인 ID는 바꾸지 않습니다.
- 같은 고민의 다른 시점 기록은 한 ID로 묶고 출처를 모두 남깁니다. 판단이 다르면 나눕니다.
- 고민마다: Level과 분류 이유, 자료 충실도(충분 / 일부 부족 / 자료 부족), TD 반영(반영 / 축소 / 누락 / 원천과 다르게 씀).
- 모호한 Level은 임시 수준과 근거를 쓰고 질문으로 남깁니다. 길이·코드 복잡도로 Level을 정하지 않습니다.
- TD에만 있고 원천 근거가 없는 주장은 §7-2 목록에 모읍니다.
- 협업·PM 고민이 많으면 사용자 요청 시 `<접두어>-협업.md`로 따로 뺍니다.

## 4단계 — 초안 (형식 칸 먼저 채우기)

[references/file-template.md](references/file-template.md)의 골격으로 분류 파일을 씁니다.

- **먼저 채우고 묻습니다.** 참고 범위 문서(원천·TD·intake 답·report 결정)에 형식 칸에 맞는 내용이 있으면 출처와 `(추론)`을 달아 채웁니다. 원천에 매몰되어 "원천에 없음"만 쓰지 않습니다.
- 근거가 없거나 애매한 칸만 `🟡 구체화 필요 (Q-번호)`로 둡니다.
- **L1의 빈 칸은 질문 대신 §3 면접 대비 취약점(V-번호)** 으로 옮깁니다. 예상 면접 질문과 원천에 없는 이유를 적습니다. 형식 칸이 통째로 빈 L1만 질문으로 남깁니다.
- 제약 조건 칸은 억지로 묻지 않습니다. 버그류는 트러블슈팅 꼴(증상·에러 화면 → 원인 → 해결), 원인을 모르는 버그는 추정 원인을 쓰지 않고 "이런 문제를 이렇게 예방했다" 꼴로 둡니다.
- 질문은 별도 표로 모으지 않고 §1 고민 상자 안에 둡니다. 순서는 답이 필요한 고민(높음 → 보통) → 보류만 남음 → 끝남.
- 질문 쓰는 법은 [references/questions-and-dialogue.md](references/questions-and-dialogue.md) §1: 볼 원천과 답할 내용을 구체적으로, 예시 선택지 붙이기, 이미 답한 것 다시 묻지 않기, Claude가 찾을 수 있는 것은 먼저 찾기.
- 검사: `python .claude/skills/tech-doc-issue-summary/scripts/check_quotes.py <분류 파일> <별칭표.tsv>` 불일치 0(7단계로 기술 문서를 고친 뒤에는 `TD` 줄 번호가 밀려 TD 행만 불일치가 나는 것이 정상), 본문 🟡·⏸ 번호와 §1 질문 번호 일치, 원천 md의 제목·목록 줄을 훑어 어느 ID에도 안 걸린 줄은 §7-1에 "누락"으로. **다 확인했다고 쓰지 않습니다.** 못 본 자료는 못 봤다고 씁니다.
- `INDEX.md`를 갱신하고, 맺는 메시지에 우선순위 높은 질문과 Level이 애매한 고민을 먼저 보여 줍니다. 사용자는 파일의 질문 아래에 탭으로 들여써 답을 답니다.

## 5단계 — 답 반영 (차수별)

[references/questions-and-dialogue.md](references/questions-and-dialogue.md) §2 체크리스트를 따릅니다. 요지:

1. 작업 전 분류 파일 사본을 `%TEMP%\gomin\<이름>.before-sN.md`로 둡니다.
2. 탭으로 들여쓴 줄(또는 사본과 diff)로 답을 찾고 개수를 셉니다. 바로 위 `**Q-번호**`로 어느 질문의 답인지 봅니다. 상자가 지워진 듯하면 사본에서 되살리고 맨 먼저 알립니다.
3. 코드 확인이 필요한 답은 **그 답이 가리킨 범위만** 하위 에이전트에게 맡기고, 그동안 나머지를 반영합니다.
4. §6 고민 칸에 `💬 사용자 답 (날짜 N차): “원문 그대로”`, B 대응표에 `사용자 답 (날짜 N차)` 행, C에 `[풀림 날짜 N차]`·`[충돌]`·`[누락]`.
5. 풀린 🟡는 지우고 "옛 Q-n"으로 적습니다. 새 질문은 마지막 번호에 이어 붙이고, 지운 번호는 다시 쓰지 않습니다. "나중·후순위·별도 세션"은 ⏸ 보류로 §2에.
6. Level·충실도가 바뀌면 이유 한 줄. 사용자가 추정을 쓰지 말라고 하면 본문에서 지우고 C에 요지를 남깁니다. 답이 원천·TD와 어긋나면 양쪽을 남기고 "충돌".
7. §1 상자 재배치, 맨 위 차수 `[!summary]`(지난 차수는 접힘), §2·§3·§5 결과 수·§7·§8·`INDEX.md` 갱신, 4단계 검사 다시.
8. 맺는 메시지: 반영한 답 줄 수, 풀린·남은·새·보류 질문, Level 변경, 읽은 코드 범위, **애매했던 줄**("…로 읽었습니다").

사용자가 "따로 티키타카"라고 한 질문은 ⏸로 두고 6단계 대화 세션을 엽니다(사용자가 열어 달라고 할 때).

## 6단계 — 대화 세션 (티키타카)

기억이 흐린 질문 하나를 코드·원천을 함께 보며 푸는 별도 세션입니다. 진행 틀과 결과 파일 골격은 [references/questions-and-dialogue.md](references/questions-and-dialogue.md) §3.

- 여는 쪽: `start_session`(fresh)에 배경·정리할 것 ①②③·먼저 읽을 것·볼 코드 범위(모르면 "사용자에게 물어 받은 범위만")·진행 규칙·결과 파일을 넣고, 전역 규칙대로 바로 연결을 끊습니다.
- 대화 쪽: 코드 조각 → 그 코드가 하는 일 한 문단 → 질문 1~2개. 갈림길은 (가)/(나), 수준이 여럿이면 후보 표. "기억나는 만큼만, 모르겠음도 괜찮습니다."
- 결과는 `<접두어>-Q<n>-대화.md`에 회차별(**[코드]**·**[기억]**·`(추정)`·`(추론)`)로 쓰고, 끝에 「결과 정리」(정해진 것·남은 것·기술 문서 문장 후보·Claude 의견).
- 분류 파일·기술 문서는 사용자가 허락할 때만, 직전에 다시 읽고 해당 칸만 고칩니다.

## 7단계 — 기술 문서 반영 (사용자가 요청할 때만)

[references/to-tech-doc.md](references/to-tech-doc.md)의 매핑을 따릅니다. 요지:

- 근거는 분류 파일의 사용자 답(💬·대응표)과 원천 발췌뿐입니다. `(추론)`·⏸ 보류·V-취약점은 넣지 않습니다.
- L3 → 고민과 선택 절, L2 → 트러블슈팅 묶음·기존 비교 절·구현 절의 "계기", L1 → 1~3줄 보충 또는 아쉬운 점.
- 고민과 무관한 줄, 사용자가 직접 고친 줄은 그대로 둡니다(`git diff`로 먼저 확인). 문체는 지금 기술 문서를 따릅니다.
- 그림은 만들지 않고 분류 파일 §8 사진 목록을 report 촬영 요청으로 옮깁니다.
- 끝나면 `/portfolio-build <폴더>` → `deck-edits.py apply --all` → `python .claude/skills/portfolio-build/portfolio-edits.py apply --all`. `/portfolio-edit`로 고정한 장면이 바뀐 내용과 충돌하는지 봅니다.
- `report/<폴더>.md` 맨 위에 반영 목록(근거 열에 `별칭:L줄`·Q-번호)·비운 곳·「확인해 주세요」(Claude가 문장으로 옮긴 곳)를 쓰고, 루트 `report.md`를 요약판으로 다시 씁니다.

## 하지 않는 것

- 커밋하지 않습니다. `report/`는 git 제외입니다. 기술 문서 커밋은 사용자 요청 때만.
- 1~6단계에서는 `src/`·`data/`를 고치지 않습니다.
- 현재 코드만 보고 당시 판단을 추측하지 않습니다. 현재 구현이 이전 설계보다 낫다고 단정하지 않습니다.
