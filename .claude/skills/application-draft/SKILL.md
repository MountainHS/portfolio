# /application-draft — 지원서 초안 쓰기

> 규칙: `.claude/rules/application-writing.md`(D1~D7 자소서 문항, P1~P6 프로젝트 이력). 이 스킬을 시작하면 먼저 Read한다.
> 본보기: `report/지원서-형식-비교.md`(초안 ↔ 제출본 전후 문장), `report/넷마블네오-자소서.md` 「제출본」(최근 제출 전문).
> 지어내지 않는다(루트 `CLAUDE.md` 원칙 1). 소스에 없는 사실은 질문으로 묻는다.

## 인자

| 인자 | 하는 일 |
|---|---|
| `<회사>` 또는 `<회사> 시작` | 1~4단계: 작업 파일 만들기 → 소재 배치 → 질문 → 초안 |
| `<회사> 답 반영` | 맨 위 질문의 답을 읽고 초안 다음 차수를 쓴다(5단계까지) |
| `<회사> 점검` | 5~6단계만: 글자 수와 점검표 |
| `<회사> 수정본 비교` | 7단계: 사용자가 고친 최종본과 초안 비교 → 규칙 갱신 제안 |

## 1. 공고와 칸 모으기

- 사용자에게 받을 것: 공고 원문(또는 스크린샷) · 문항 원문과 글자 수 상한 · 마감 · 지원서의 다른 칸(프로젝트 이력 칸 이름·상한, 고르는 칸 선택지).
- 받은 것이 없으면 이것만 묻고 멈춘다. 문항을 짐작해 쓰지 않는다.
- 작업 파일 `report/<회사>-자소서.md`를 만든다(`report/`는 gitignore). 틀:

~~~md

> 독자: 인사담당자 → 시니어 개발자. 표준 기술 용어 그대로, 곁가지 예시 없이(.claude/rules/application-writing.md).
~~~

## 2. 소재 모으기와 배치

- 읽는 순서(앞에 있을수록 먼저 재사용):
  1. 직전 제출본 `report/넷마블네오-자소서.md` 「제출본」 — 같은 성격의 문항·이력 칸이면 이 글에서 출발한다.
  2. 같은 파일의 「확정 사항」 — 쓰지 않기로 한 것(91%·세부 수치·스터디장 등)과 사실 결정.
  3. `data/projects/*.json` — 역할·highlights·troubleshooting·retro.
  4. `src/*/기술문서.md` — 위에서 모자란 근거만 Grep으로 찾아 그 절만 읽는다.
- 「문항별 배치」 표를 채운다. 같은 장면을 같은 결론으로 두 문항에 쓰지 않는다. 중심 소재는 강조일 뿐이고, 다른 프로젝트의 좋은 장면은 보조로 쓴다.
- 새 공고의 직무 특성(지원동기 D4의 마지막 문장 재료)은 공고 원문에서 한 줄로 뽑아 「확정 사항」에 적는다.

## 3. 질문

- 질문은 작업 파일 맨 위 「질문」 한 곳에만, 각 질문 아래 빈 답 줄. 본문에 같은 질문을 다시 쓰지 않는다.
- 먼저 채우고 묻는다: 소스로 쓸 수 있는 칸은 초안을 쓰고, 근거가 없는 칸(D3의 "결과", D4의 전환점, 회사 관련 경험)만 묻는다.
- 답이 끝난 차수는 「이전 기록」으로 내린다.

## 4. 초안 쓰기

- `application-writing.md`의 D·P 규칙으로 쓴다. 문항 유형별로 따를 규칙:

| 문항 유형 | 규칙 |
|---|---|
| 지원동기 | D4 + D1·D6 |
| 협업·갈등·실패 경험 | D3 + D2 |
| 게임 분석 | D7 |
| 역량 개발·준비 과정 | D5 |
| 강점·약점 | D3(약점 끝은 지금 하는 개선) + D1 |
| AI·도구 활용 방식 | 번호 목록 절차, D1·D6 |
| 프로젝트 이력 칸 | P1~P6 |

- 문항마다 본문 바로 뒤에 `<details>` 사실 확인: 문장별 출처(제출본·data 경로·기술문서 줄·사용자 답 차수). Claude가 새로 줄이거나 바꾼 문장은 그렇다고 적는다.
- 이전 차수 초안은 지우지 않고 「이전 기록」으로 내린다. 새 차수 맨 위에 "바꾼 것" 목록을 둔다.

## 5. 글자 수

```powershell
python .claude/skills/application-draft/count.py report/<회사>-자소서.md
```

- ` ```text ` 블록마다 공백 포함·공백 제외·줄바꿈 2자 세 값을 낸다. 제목으로 나뉜 md(예: 사용자가 준 최종본)는 `--sections`.
- 「글자 수」 표를 갱신한다. 상한의 85~100%를 목표로 하고, 줄바꿈 2자 기준으로도 넘지 않는지 본다.

## 6. 점검

- `application-writing.md` 「내보내기 전 점검」 목록을 문항마다 돌린다.
- 걸린 것은 고치고, 고칠 수 없는 것(근거 부족)은 질문으로 올린다.
- 사용자가 직접 고친 문장은 요청 없이 다시 고치지 않는다.

## 7. 수정본 비교 (피드백 고리)

- 사용자가 제출본(직접 고친 최종)을 주면:
  1. 작업 파일 맨 위에 「제출본」 절로 옮기고 글자 수를 잰다.
  2. 마지막 초안과 문단마다 비교해 `report/지원서-형식-비교.md` 형식(초안 | 제출본 | 태그) 표를 새 회사 절로 덧붙인다.
  3. 기존 D·P 규칙으로 설명되지 않는 차이만 골라, 규칙 추가·수정안을 사용자에게 보여 주고 확인받은 뒤 `application-writing.md`에 반영한다.
- 이번 회사에서만 쓰인 결정(회사 이름·특정 사건)은 규칙에 넣지 않고 작업 파일 「확정 사항」에만 둔다.
