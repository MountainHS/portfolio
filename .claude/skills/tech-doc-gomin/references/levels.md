# Level 정의와 형식 칸

> 출처: 2026-11-12 최초 세션 "프로젝트 기술 고민 자료 분류 및 정리 계획"에 사용자가 붙인 작업 지시문. §1~§4·§5 일부·§10은 **원문 그대로** 옮겼습니다. 끝의 「WGO에서 정한 것」만 이후 사용자 답으로 더한 규칙입니다.

## 발굴 기준 (지시문 §3 원문)

다음과 같은 내용은 모두 기록할 가치가 있다.

- 어떤 문제가 발생했는가?
- 처음에는 무엇이 문제라고 생각했는가?
- 왜 그 방법을 선택했는가?
- 다른 해결 방법을 고민했는가?
- 어떤 제약 때문에 특정 방법을 포기했는가?
- 처음 생각한 방법이 예상대로 작동했는가?
- 어떤 문제가 새롭게 발생했는가?
- 왜 기존 설계를 수정했는가?
- AI에게 무엇을 요청했고, 그 결과를 어떻게 평가했는가?
- 해결하지 못한 문제나 미래에 개선하려던 내용이 있는가?
- 개발 당시와 현재의 판단이 달라졌는가?

**최종 구현에 반영되지 않았더라도 개발자의 판단 과정에 영향을 준 고민은 보존해야 한다.**

예를 들어:

- 고려했다가 포기한 아키텍처
- 실제 구현하지 못한 개선안
- 테스트했지만 효과가 없었던 최적화
- 일정 문제로 선택한 임시 해결책
- AI에게 잘못 요청해 발생한 문제
- 팀원과 협업하면서 발견한 설계상의 문제

고민마다 고유 ID를 부여하라. ID는 이후 모든 표와 정리 결과에서 동일하게 유지한다.
하나의 고민이 여러 문서에 나타나면 가급적 하나의 ID로 묶되, 서로 다른 판단이나 문제를 지나치게 합치지 마라.

## Level 1 — Micro Decision Log

작은 기술적 판단이나 비교적 단순한 문제 해결 기록.

예시:

- 특정 API를 선택한 이유
- 간단한 코드 구조 변경
- 작은 버그 수정 과정
- 단일 AI 프롬프트를 통한 문제 해결
- 기존 구현에 사소한 조건을 추가한 이유

기록할 핵심 정보 (형식 칸 4개):

1. 문제 상황
2. 선택한 방법과 판단 이유
3. 적용 결과
4. 남은 문제 또는 배운 점

작은 고민이라도 판단 과정이 있다면 버리지 마라.

## Level 2 — Technical Decision & Iteration Log

여러 대안이나 시행착오를 동반한 의미 있는 기술적 의사결정.

예시:

- 시스템 아키텍처 선택
- 상태 머신 구조 설계
- 네트워크 동기화 방식 결정
- AI를 반복 사용하며 설계 개선
- 복잡한 버그의 원인 분석과 해결
- 성능 개선을 위한 여러 방식의 비교
- 반복적인 리팩토링 과정

기록할 핵심 정보 (형식 칸 10개):

1. 문제 상황 및 목표
2. 제약 조건
3. 고려한 대안
4. 최초 판단과 선택 이유
5. 적용한 방법
6. 예상과 실제 결과
7. 실패 및 새로운 문제
8. 판단 변경과 재시도
9. 최종 결과의 장단점
10. 개선 방향과 배운 점

**시행착오가 여러 차례 있었다면 시도별로 구분해서 보존해야 한다.**

## Level 3 — Portfolio Case Study 후보

프로젝트의 핵심적인 기술적 역량을 보여줄 수 있는 대표 사례.

예시:

- 프로젝트에서 가장 중요한 시스템의 설계와 개선
- 기술적 난도가 높았던 문제 해결
- 여러 제약 사이에서 명확한 판단 기준을 세운 사례
- 실제 측정과 검증을 통해 설계를 개선한 사례
- 실패 이후 설계를 크게 수정한 사례
- 협업 전체에 영향을 준 기술적 결정

기록할 핵심 정보 (형식 칸 7개):

1. 문제의 중요성과 프로젝트 맥락
2. 개발자가 직접 내린 기술적 판단
3. 대안과 선택 근거
4. 중요한 시행착오와 설계 변경
5. 구현 결과와 검증 자료
6. 장단점 및 개선 방향
7. 포트폴리오에서 강조할 수 있는 기술적 역량

## 분류 시 주의사항 (원문)

- Level 3는 단순히 Level 2보다 기술 난도가 높은 항목을 의미하지 않는다. **포트폴리오의 대표 사례로 발전시킬 가치가 있는 항목**이다.
- Level 3로 분류해도 Level 2 수준의 상세한 원본 기록은 보존해야 한다.
- 현재 기준에서 중요하지 않아 보인다는 이유로 Level 1 고민을 삭제하지 마라.
- 분류가 모호하면 임시 수준과 판단 근거를 기록하고 사용자 검토 대상으로 남겨라.
- 문서의 길이와 코드의 복잡도만으로 수준을 판단하지 마라.

WGO 파일에서는 L3를 "L2 10칸 흐름 + `**L3 — 문제의 중요성:**`·`**L3 — 개발자가 직접 내린 판단:**`·`**L3 — 강조할 수 있는 역량:**` 줄"로 썼습니다(L3 7칸 중 나머지는 L2 칸과 겹침). `WGO.md` §6 WGO-D-001이 본보기입니다.

## 대응 상태 (원문)

- **명확:** 정리한 내용이 원본에 직접적으로 존재함
- **일부:** 여러 근거를 조합해야 하거나 일부만 확인됨
- **추론:** 원본에 직접적인 설명이 없으며 정리가 해석에 의존함
- **미확인:** 이를 뒷받침하는 근거를 찾지 못함

추론 내용은 확인된 사실과 문장 수준에서도 구분하라. (WGO에서 더한 것: 사용자 답과 원천·TD가 어긋나면 **충돌**, 사용자 답 행은 `명확 (사용자 답)`.)

## 누락 및 손실 점검 — C 칸에서 볼 것 (원문)

- 정리하지 않은 원본 고민이 있는가?
- 고려했지만 선택하지 않은 대안이 사라졌는가?
- 실패하거나 폐기된 방법이 누락되었는가?
- AI 프롬프트 변경 과정이 사라졌는가?
- 다른 문서와 모순되는 내용이 있는가?
- 최종 코드만 보고 추정한 내용을 사실처럼 기술했는가?
- 최초 설계와 최종 구현의 차이가 드러나는가?
- 원본에서는 중요하게 언급했지만 1차 정리에서 축소된 내용이 있는가?

발견한 항목은 삭제하거나 임의로 해결하지 말고 별도로 기록하라.

## 작업 제약 (원문)

1. 기존 파일을 수정하거나 삭제하지 마라.
2. 완성된 기술문서를 작성하지 마라.
3. 원본을 재작성하거나 요약하는 과정에서 고민을 임의로 제거하지 마라.
4. 자료에 없는 개발자의 의도나 생각을 만들어내지 마라.
5. 불명확한 내용은 추론으로 확정하지 말고 확인 필요 사항으로 표시하라.
6. 현재 구현이 이전 설계보다 우수하다고 단정하지 마라.
7. 동일한 고민을 다룬 자료가 여러 개라면 통합할 수 있지만, 원본 출처는 모두 유지하라.
8. 원본 자료가 많다고 해서 주요 고민을 임의로 생략하지 마라.

(1·2는 1~6단계에 적용합니다. 7단계 기술 문서 반영은 사용자 요청이 있을 때만 기술 문서를 고칩니다.)

## 성공 기준 (지시문 §10 원문)

1. 원본에 존재했던 중요한 고민이 사라지지 않았는가?
2. 개발자의 최초 판단과 이후 판단 변화가 구분되는가?
3. 정리된 내용이 원본의 어디에서 왔는지 확인할 수 있는가?
4. 원본에 없는 내용을 AI가 임의로 보충하지 않았는가?
5. 사용자가 1차 정리 결과를 보고 분류 및 정리 방향에 대해 구체적으로 피드백할 수 있는가?

**최종 구현보다 그 구현에 도달하기까지의 사고 과정이 이번 작업의 핵심 자료다.**
원본의 불완전한 문장, 실패한 생각, 모순된 판단, 해결되지 않은 고민까지 중요한 기록으로 취급하라.

## WGO에서 정한 것 (2026-11-16 사용자 답)

- **먼저 채우고 묻기:** “자꾸 원천에 너무 매몰되는거 같은데 너가 참고한 문서 범위에서 관련 내용 있고 현재 레벨 3, 2, 1 형식에 맞으면 일단 채워넣고 질문해줘.”
- **L1 질문 → 취약점 목록:** “나머지 L1 질문들은 취약점 목록으로 넣고 거기중에서 내가 구체화해야하는 (원천 소스에 없음 말고 형식에 들어갈 내용이 부족한 경우만 한정)”
- **제약 칸은 억지로 묻지 않기:** “얘는 제약 조건을 굳이 구체화해야할까? 제약조건 쓸 지점이 아니라 원자성을 이용한 코드로 이러한 문제를 예방했다가 좋을 것 같아.”
- **원인 모를 버그는 예방 꼴:** “진짜 원인 모를 버그여서 섣불리 추정 내용 적는게 아니라 이런 문제 예방했다 방식으로 적는게 좋을거 같아.”
- **버그는 트러블슈팅:** “내가 볼때는 이건 트러블슈팅? 유니티 관련 에러 띄워서 하면 될거 같음”
- **정확한 일자:** “정확한 일자는 기술문서에 안 적혀도 돼. 이건 모든 기술 문서에 다 동일하게 적용해줘” (분류 파일에는 남겨도 됨)

## Level을 바꾼 실제 예 (WGO)

| 고민 | 바꿈 | 근거 |
|---|---|---|
| D-026 기획 방향·범위 변화 | L3 후보 → L2 | 사용자 “L3는 아닌거 같아.” |
| D-008 서버 원자성 버그 | L2 → L1 | 원인 모를 버그, "예방" 꼴로 짧게 |
| D-027 Codex 피드백 효과 추천 | L2 → L1 | Codex 기록 소실, 아쉬운 점에 한 문장 |
| D-005 데이터 생명주기 | L2 → L3 | 사용자 “올려도 될거 같아”, 시도 1~3 원문이 충분 |
| D-011 데이터·로직·뷰 분리 | L2 → L1 | 사용자 답(다리 개수 버그는 트러블슈팅으로 분리) |

Level을 바꾸면 고민의 `분류` 줄에 `Level 1 (옛 L2)`처럼 남기고, `분류 이유`에 무엇 때문에 바꿨는지 한 줄을 씁니다.
